# Сравнение LLM-сгенерированных пайплайнов для IoT malware detection

Репозиторий содержит артефакты эксперимента по курсу "Протоколы Интернета Вещей". Цель эксперимента: проверить, насколько хорошо разные LLM могут сгенерировать рабочий Python-пайплайн для анализа IoT-сетевого трафика и бинарной классификации соединений из CTU-IoT-Malware-Capture.

Задача для всех сгенерированных решений одна и та же: по Zeek/Bro `conn.log` CSV определить, является ли соединение benign или malicious.

## Что сравнивается

В эксперименте менялись три фактора:

| Фактор | Варианты |
| --- | --- |
| LLM | GPT 5.5, Gemini 3.1 Pro |
| Язык промпта | английский, русский |
| IP-признаки | без сырых IP по умолчанию, с `--include-ip` |

Сырые IP-адреса (`id.orig_h`, `id.resp_h`) намеренно вынесены в отдельный режим: они могут дать сильное переобучение на конкретные C&C-адреса и резко увеличивают размер one-hot-пространства.

## Состав репозитория

| Файл | Назначение |
| --- | --- |
| `prompt_en_10.txt` | финальная англоязычная версия промпта |
| `prompt_ru_10.txt` | финальная русскоязычная версия промпта |
| `gpt_5-5_generated_en.py` | код, сгенерированный GPT 5.5 по английскому промпту |
| `gpt_5-5_generated_ru.py` | код, сгенерированный GPT 5.5 по русскому промпту |
| `gemini_3-1_pro_generated_en.py` | код, сгенерированный Gemini 3.1 Pro по английскому промпту |
| `gemini_3-1_pro_generated_ru.py` | код, сгенерированный Gemini 3.1 Pro по русскому промпту |
| `results.zip` | первичный прогон на полных CSV для части capture |
| `results_sampled.zip` | основной прогон на 10 capture с сэмплированием крупных CSV до 200 000 строк |

## Как формировались промпты

Сначала была вручную описана постановка задачи: формат Zeek/Bro `conn.log`, особенности CTU-IoT-Malware-Capture, требования к обработке пропусков, запрет на leakage через `detailed-label`, запрет на `uid`, два режима работы с IP и набор метрик.

После этого GPT 5.5 в режиме рассуждения использовался для генерации первого варианта промпта. Полученный промпт проверялся в отдельном чате на качестве итогового кода, затем итеративно улучшался: модель просили переписать и усилить предыдущую версию промпта. Такой цикл повторялся отдельно для английского и русского языков, пока генерируемый код визуально и по поведению не стал достаточно качественным для сравнения.

Итогом стали два финальных промпта (`prompt_en_10.txt`, `prompt_ru_10.txt`) и четыре независимых сгенерированных Python-скрипта.

## Требования к задаче

Все промпты требовали от модели построить полноценный ML-пайплайн:

- загрузить CSV через `pandas`;
- заменить `-` на пропуски;
- удалить дубликаты;
- нормализовать значения `label`;
- сформировать бинарную цель: `Benign -> 0`, все метки с `Malicious -> 1`;
- исключить из признаков `label`, `detailed-label`, `uid`;
- по умолчанию исключить `id.orig_h` и `id.resp_h`;
- добавить режим `--include-ip` для обучения с IP-адресами;
- добавить простые engineered features: `history_len`, `bytes_ratio`, `pkts_ratio`, `total_bytes`, `total_pkts`, `hour`, `dayofweek`;
- использовать `Pipeline` и `ColumnTransformer`;
- обучить минимум три модели;
- сохранить метрики, отчеты, confusion matrix, список признаков и лучшую модель.

Типичные модели в сгенерированных решениях: `LogisticRegression`, `RandomForestClassifier`, `GradientBoostingClassifier` или `HistGradientBoostingClassifier`.

## Установка зависимостей

Минимальный набор библиотек:

```bash
python -m venv .venv
source .venv/bin/activate
pip install pandas numpy scikit-learn matplotlib seaborn joblib
```

## Пример запуска

Все четыре скрипта имеют одинаковую идею CLI: путь к CSV, папка для результатов, размер test set, random seed и опциональный флаг `--include-ip`.

Запуск без сырых IP-адресов:

```bash
python gpt_5-5_generated_en.py \
  --data-path data/CTU-IoT-Malware-Capture-20-1conn.log.labeled.csv \
  --output-dir runs/gpt_en_no_ip
```

Запуск с IP-признаками:

```bash
python gpt_5-5_generated_en.py \
  --data-path data/CTU-IoT-Malware-Capture-20-1conn.log.labeled.csv \
  --output-dir runs/gpt_en_ip \
  --include-ip
```

Аналогично можно запускать:

```bash
python gpt_5-5_generated_ru.py --data-path <csv> --output-dir <out>
python gemini_3-1_pro_generated_en.py --data-path <csv> --output-dir <out>
python gemini_3-1_pro_generated_ru.py --data-path <csv> --output-dir <out>
```

## Что сохраняет каждый запуск

Точные имена подпапок немного отличаются между GPT- и Gemini-скриптами, но в целом каждый успешный запуск сохраняет:

- `metrics.csv` со сравнением моделей;
- `classification_report` для каждой модели;
- `confusion_matrix` для каждой модели;
- `best_model.joblib`;
- `features.json`;
- `summary.txt`;
- EDA-артефакты: распределение классов, пропуски, числовая статистика, графики портов, протоколов и состояний соединений;
- `run.log` при пакетном запуске.

После распаковки архивов полезнее всего начинать с `run_log.csv`: он показывает dataset, variant, статус, время выполнения, return code и папку с конкретными результатами.

```bash
unzip results_sampled.zip
less results_sampled/run_log.csv
```

## Прогоны и сэмплирование

### `results.zip`

Первичный прогон на полных CSV для части capture. В `run_log.csv` отражены capture `1-1`, `3-1`, `20-1`, `34-1`.

Общая картина:

- варианты без IP успешно прошли на этих capture;
- IP-варианты успешно прошли на малых `20-1` и `34-1`;
- IP-варианты падали с return code `-9` на более тяжелых `1-1` и `3-1`, то есть процесс был убит системой из-за нехватки памяти.

### `results_sampled.zip`

Основной прогон по 10 capture:

```text
1-1, 3-1, 8-1, 9-1, 20-1, 34-1, 35-1, 42-1, 44-1, 48-1
```

Для крупных CSV использовалась стратифицированная выборка до 200 000 строк с сохранением баланса классов. В этот режим попали крупные capture `1-1`, `9-1`, `35-1`, `48-1`; меньшие capture копировались без урезания.

Результат:

- все варианты без IP завершились успешно на всех 10 capture;
- IP-варианты прошли на `8-1`, `20-1`, `34-1`, `42-1`, `44-1`;
- IP-варианты упали с `-9` на `1-1`, `3-1`, `9-1`, `35-1`, `48-1`.

Главная причина падений: не размер CSV сам по себе, а высокая кардинальность IP-адресов. При `--include-ip` скрипты строят плотный one-hot по `id.orig_h` и `id.resp_h`; для capture с большим количеством уникальных IP это дает слишком широкую матрицу.

### `results_sampled_20k.zip`

Дополнительный прогон только для упавших IP-вариантов. Пять проблемных capture (`1-1`, `3-1`, `9-1`, `35-1`, `48-1`) были дополнительно сэмплированы до 20 000 строк.

В этом архиве запускались только четыре IP-варианта:

```text
gemini_en_ip
gemini_ru_with_ip
gpt_en_ip
gpt_ru_ip
```

Все 20 запусков завершились успешно. Это подтверждает, что проблема была не в невозможности обучить модели в принципе, а в памяти и размерности dense one-hot-представления для IP-признаков.

## Как интерпретировать эксперимент

Важная часть методологии: сгенерированные LLM-скрипты не правились вручную перед сравнением. Ограничения по памяти выносились наружу через подготовку данных и сэмплирование. Это сохраняет честность сравнения качества кода, который выдали модели.

Основной вывод по артефактам:

- все четыре LLM-сгенерированных решения умеют запускаться end-to-end и сохранять ожидаемые артефакты;
- без IP-признаков пайплайны стабильно проходят на 10 capture при сэмплировании крупных файлов до 200 000 строк;
- режим с IP-признаками плохо масштабируется из-за плотного one-hot-кодирования адресов;
- более жесткий сэмпл до 20 000 строк позволяет завершить тяжелые IP-прогоны, но это скорее обход ограничения памяти, чем хорошая архитектура для production-пайплайна.

## Ограничения воспроизводимости

В репозитории лежат сами промпты, сгенерированные скрипты и архивы результатов. Для полного повторения эксперимента нужны исходные CSV из CTU-IoT-Malware-Capture и внешний скрипт/процедура пакетного запуска и сэмплирования, которые использовались при подготовке архивов.

При повторном запуске на других версиях `pandas`, `scikit-learn` или на другой машине время выполнения и падения по памяти могут отличаться.
