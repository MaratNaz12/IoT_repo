# Сравнение LLM-сгенерированных пайплайнов для IoT malware detection

Репозиторий содержит артефакты эксперимента по курсу "Протоколы Интернета Вещей". Цель эксперимента: проверить, насколько хорошо разные LLM могут сгенерировать рабочий Python-пайплайн для анализа IoT-сетевого трафика и бинарной классификации соединений из CTU-IoT-Malware-Capture.

Задача для всех сгенерированных решений одна и та же: по Zeek/Bro `conn.log` CSV определить, является ли соединение benign или malicious.

## Что сравнивается

В эксперименте менялись три фактора:

| Фактор | Варианты |
| --- | --- |
| LLM | GPT 5.5, Gemini 3.1 Pro |
| Язык промпта | английский, русский |
| IP-признаки | без сырых IP по умолчанию, с `--include-ip` |

Сырые IP-адреса (`id.orig_h`, `id.resp_h`) намеренно вынесены в отдельный режим: они могут дать сильное переобучение на конкретные C&C-адреса и резко увеличивают размер one-hot-пространства.

## Структура проекта

```text
.
├── README.md                      - этот файл
├── requirements.txt               - зависимости Python
├── .gitignore
│
├── prompts/                       - промпты, поданные в LLM
│   ├── prompt_en_10.txt
│   └── prompt_ru_10.txt
│
├── llm_generated/                 - код, сгенерированный LLM
│   ├── gemini_3-1_pro_generated_en.py
│   ├── gemini_3-1_pro_generated_ru.py
│   ├── gpt_5-5_generated_en.py
│   └── gpt_5-5_generated_ru.py
│
├── additional_scripts/            - вспомогательные скрипты
│   ├── sample_data.py
│   └── run_all.py
│
└── results.zip                    - единый архив результатов эксперимента
```

После распаковки `results.zip` создается папка `results/`. Внутри нее результаты разложены по схеме `results/<вариант>/<датасет>/`, а общая сводка всех запусков лежит в `results/run_log.csv`.

Сырые CSV-файлы датасета в репозиторий не включены. Для повторного запуска их нужно положить локально, например в папку `data/`.

## Как формировались промпты

Сначала была вручную описана постановка задачи: формат Zeek/Bro `conn.log`, особенности CTU-IoT-Malware-Capture, требования к обработке пропусков, запрет на leakage через `detailed-label`, запрет на `uid`, два режима работы с IP и набор метрик.

После этого GPT 5.5 в режиме рассуждения использовался для генерации первого варианта промпта. Полученный промпт проверялся в отдельном чате на качестве итогового кода, затем итеративно улучшался: модель просили переписать и усилить предыдущую версию промпта. Такой цикл повторялся отдельно для английского и русского языков, пока генерируемый код визуально и по поведению не стал достаточно качественным для сравнения.

Итогом стали два финальных промпта (`prompts/prompt_en_10.txt`, `prompts/prompt_ru_10.txt`) и четыре независимых сгенерированных Python-скрипта в `llm_generated/`.

## Требования к задаче

Все промпты требовали от модели построить полноценный ML-пайплайн:

- загрузить CSV через `pandas`;
- заменить `-` на пропуски;
- удалить дубликаты;
- нормализовать значения `label`;
- сформировать бинарную цель: `Benign -> 0`, все метки с `Malicious -> 1`;
- исключить из признаков `label`, `detailed-label`, `uid`;
- по умолчанию исключить `id.orig_h` и `id.resp_h`;
- добавить режим `--include-ip` для обучения с IP-адресами;
- добавить простые engineered features: `history_len`, `bytes_ratio`, `pkts_ratio`, `total_bytes`, `total_pkts`, `hour`, `dayofweek`;
- использовать `Pipeline` и `ColumnTransformer`;
- обучить минимум три модели;
- сохранить метрики, отчеты, confusion matrix, список признаков и лучшую модель.

Типичные модели в сгенерированных решениях: `LogisticRegression`, `RandomForestClassifier`, `GradientBoostingClassifier` или `HistGradientBoostingClassifier`.

## Установка зависимостей

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

В примерах ниже используется `python` из активированного виртуального окружения. Если окружение не активировано, на macOS часто нужно заменить `python` на `python3`.

## Ручной запуск одного скрипта

Все четыре LLM-скрипта имеют одинаковую идею CLI: путь к CSV, папка для результатов, размер test set, random seed и опциональный флаг `--include-ip`.

Запуск без сырых IP-адресов:

```bash
python llm_generated/gpt_5-5_generated_en.py \
  --data-path data/CTU-IoT-Malware-Capture-20-1conn.log.labeled.csv \
  --output-dir runs/gpt_en_no_ip
```

Запуск с IP-признаками:

```bash
python llm_generated/gpt_5-5_generated_en.py \
  --data-path data/CTU-IoT-Malware-Capture-20-1conn.log.labeled.csv \
  --output-dir runs/gpt_en_ip \
  --include-ip
```

Аналогично можно запускать:

```bash
python llm_generated/gpt_5-5_generated_ru.py --data-path <csv> --output-dir <out>
python llm_generated/gemini_3-1_pro_generated_en.py --data-path <csv> --output-dir <out>
python llm_generated/gemini_3-1_pro_generated_ru.py --data-path <csv> --output-dir <out>
```

## Вспомогательные скрипты

### `additional_scripts/sample_data.py`

Скрипт берет CSV из `data/` и делает их уменьшенные копии в отдельной папке (`data_sampled/` по умолчанию), сохраняя баланс классов Benign / Malicious. Маленькие файлы он просто копирует; большие урезает до заданного числа строк; очень большие читает по кускам, чтобы не упасть по памяти.

Запуск по умолчанию: до 200 000 строк, результат в `data_sampled/`.

```bash
python additional_scripts/sample_data.py
```

Жесткий сэмпл для вариантов с IP-адресами: до 20 000 строк, результат в `data_sampled_20k/`.

```bash
python additional_scripts/sample_data.py --dst data_sampled_20k --max-rows 20000 --size-threshold-mb 5
```

### `additional_scripts/run_all.py`

Главный скрипт эксперимента: запускает все варианты LLM-моделей по всем датасетам и собирает результаты в одном месте. Без него пришлось бы вручную выполнять 80 однотипных команд: 10 датасетов x 8 конфигураций, то есть Gemini/GPT, английский/русский промпт, с IP / без IP.

Скрипт берет CSV из указанной папки (`--data-dir`), пропускает два датасета, которые использовались при обучении исходных моделей, и для каждой пары "датасет x вариант" вызывает соответствующий файл из `llm_generated/`. Результаты раскладываются по папкам вида `results/<вариант>/<датасет>/`: туда же кладутся метрики, матрицы ошибок, текстовые отчеты, сохраненная лучшая модель и подробный `run.log`. Общая сводка по всем запускам пишется в `results/run_log.csv`.

Основной прогон:

```bash
python additional_scripts/run_all.py --data-dir data_sampled --results-dir results
```

Если запуск прервался, можно дозапустить недостающее через `--skip-existing`, а для ручного подмножества использовать `--datasets` и `--variants`.

## Что сохраняет каждый запуск

Точные имена подпапок немного отличаются между GPT- и Gemini-скриптами, но в целом каждый успешный запуск сохраняет:

- `metrics.csv` со сравнением моделей;
- `classification_report` для каждой модели;
- `confusion_matrix` для каждой модели;
- `best_model.joblib`;
- `features.json`;
- `summary.txt`;
- EDA-артефакты: распределение классов, пропуски, числовая статистика, графики портов, протоколов и состояний соединений;
- `run.log` при пакетном запуске.

После распаковки архива полезнее всего начинать с `results/run_log.csv`: он показывает `dataset`, `variant`, `sample_source`, `status`, `elapsed_sec`, `returncode` и папку с конкретными результатами. Столбец `sample_source` фиксирует, как был обработан датасет перед запуском:

- `original` - файл использовался без урезания;
- `sampled_200k` - использовалась стратифицированная выборка до 200 000 строк;
- `sampled_20k` - использовалась более жесткая выборка до 20 000 строк для тяжелых IP-вариантов.

```bash
unzip results.zip
less results/run_log.csv
```

## Прогоны и сэмплирование

`results.zip` объединяет основной прогон на сэмплах до 200 000 строк и дополнительный прогон тяжелых IP-вариантов на сэмплах до 20 000 строк. В итоговой сводке 80 успешных запусков: 10 capture x 8 вариантов.

Датасеты в итоговом прогоне:

```text
1-1, 3-1, 8-1, 9-1, 20-1, 34-1, 35-1, 42-1, 44-1, 48-1
```

В `run_log.csv` видно, какой источник данных использовался для каждой пары "датасет x вариант":

- `original` для небольших capture `8-1`, `20-1`, `34-1`, `42-1`, `44-1`;
- `sampled_200k` для no-IP вариантов на крупных capture `1-1`, `3-1`, `9-1`, `35-1`, `48-1`;
- `sampled_20k` для IP-вариантов на тех же крупных capture `1-1`, `3-1`, `9-1`, `35-1`, `48-1`.

Такое разделение появилось из-за высокой кардинальности IP-адресов. При `--include-ip` скрипты строят плотный one-hot по `id.orig_h` и `id.resp_h`; для capture с большим количеством уникальных IP это дает слишком широкую матрицу и может приводить к нехватке памяти. Более жесткий сэмпл до 20 000 строк позволяет завершить тяжелые IP-прогоны, но это скорее обход ограничения памяти, чем хорошая архитектура для production-пайплайна.

## Как интерпретировать эксперимент

Важная часть методологии: сгенерированные LLM-скрипты не правились вручную перед сравнением. Ограничения по памяти выносились наружу через подготовку данных и сэмплирование. Это сохраняет честность сравнения качества кода, который выдали модели.

Основной вывод по артефактам:

- все четыре LLM-сгенерированных решения умеют запускаться end-to-end и сохранять ожидаемые артефакты;
- без IP-признаков пайплайны стабильно проходят на 10 capture при использовании оригинальных файлов или сэмплирования до 200 000 строк;
- режим с IP-признаками хуже масштабируется из-за плотного one-hot-кодирования адресов;
- при сравнении результатов важно смотреть на `sample_source`, потому что часть IP-прогонов считалась на более жестком сэмпле.

## Ограничения воспроизводимости

В репозитории лежат промпты, сгенерированные скрипты, вспомогательные скрипты и единый архив результатов. Для полного повторения эксперимента нужны исходные CSV из CTU-IoT-Malware-Capture.

При повторном запуске на других версиях `pandas`, `scikit-learn` или на другой машине время выполнения и падения по памяти могут отличаться.
